# Dependency maintenance

Use for an explicit dependency-update request, including `guardian-wrapper maintain`. This is a Guardian maintenance workflow. Matt Pocock's primary-source research, behavioral verification and separate Standards/Spec reviews inform it; the updater itself is not a Matt Pocock skill. `update` only reapplies the running wrapper's bundle to a project. `maintain` starts an interactive agent session that inspects, proposes, applies approved updates and verifies them. Neither command silently downloads a newer Guardian release.

## Inspect and propose

1. Read applicable instructions and relevant graft cards. Record the starting commit, dirty files and verification commands. Ask only for unresolved decisions: target scope, compatibility goals and major upgrades. Honor scope already supplied by the command (`app` by default, `wrapper`, `skills`, or `all`). A scope selects what to inspect; show concrete versions and changes and wait for approval before changing dependencies.
2. For `app`, discover the actual project/workspace manifests, lockfiles and package-manager/version declarations. Respect npm, pnpm, Yarn, Bun or the project's non-JavaScript tooling; do not convert package managers or invent support. Ambiguous mixed locks require clarification. Use the detected manager's read-only outdated/advisory commands and official registry/release notes. Classify direct/transitive, runtime/development, patch/minor/major and migration/security implications. Do not assume `npm outdated` exit 1 is a tool failure; distinguish normal outdated output from errors. Unsupported tooling can be inspected manually; name any unverified capability.
3. For `wrapper`, distinguish upgrading the installed Guardian release from maintaining its source repository. In a consumer project, identify the installed version/location and reviewed GitHub releases; propose an exact release installation and subsequent `guardian-wrapper update <project> --dry-run`. Never edit its installed node_modules/runtime directly. Changes to the wrapper's npm dependencies require a separate authorized source checkout. There, inspect both root build dependencies and the isolated `runtime/` graft tree. Preserve runtime security overrides, release shrinkwraps and native install behavior.
4. For `skills`, inspect `sources.lock.json`, upstream licenses, exact revisions and wrapper adaptations. Consumers upgrade to a reviewed Guardian release, then reapply their selected profile. Do not run `npx skills update/add` into wrapper-owned directories or replace them with upstream HEAD. Maintaining bundled snapshots requires an authorized wrapper source checkout: select an exact upstream commit, compare every affected skill/reference/license, preserve invocation restrictions and intentional adaptations, update the catalog if necessary, and regenerate asset hashes. A changed hash is not evidence that upstream content was reviewed.
5. Present a small plan: package/source, current and proposed version/revision, reason, affected manifests/locks/configuration, migration needs, checks and rollback boundary. Keep unrelated packages outside the batch. Get approval for concrete dependency changes unless already approved at that specificity. Do not use force audit fixes, broad `latest` upgrades or remove security overrides merely to make tooling pass.

## Apply and verify

6. Apply approved changes in a branch or isolated worktree when available, using the project's existing tooling and consistent locks. Dependency installation can execute package lifecycle scripts; respect the host's permissions and the project's script policy. Start with a small compatible batch; handle majors separately when they need migrations. Preserve pre-existing edits and do not reset the tree to roll back your batch.
7. Run a clean/frozen installation where appropriate, applicable advisory checks, typecheck, behavioral tests and build. Compare findings with the baseline. For the wrapper source also run `npm test`, `npm run typecheck`, `npm run check:assets`, `npm audit --omit=dev`, `npm audit --omit=dev --prefix runtime`, and package/consumer checks when install/runtime behavior changes. Synchronize root package-lock/npm-shrinkwrap and runtime package-lock/npm-shrinkwrap. After reviewed asset edits run `node scripts/lock-assets.mjs` before verifying assets. Package/version publication requires separate existing authorization.
8. Review the final diff against the update plan; where available, use separate Standards and Spec reviews from Matt's code-review method. Record exact versions/revisions, changed source adaptations, checks and remaining vulnerabilities. If an approved batch fails, diagnose or restore only that batch; leave it unverified until corrected. A clean audit alone does not prove application compatibility. Do not claim a dependency was updated when only its latest version was checked.

Reuse the existing work record for the proposal and results. No scheduled background updater, new memory database or duplicate dependency ledger is required.
