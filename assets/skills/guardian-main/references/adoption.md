# Adopt an existing project

Adoption maps the current project, creates coherent navigation, and consolidates documentation when justified. It does not silently refactor app code. Read integration.md and memory.md first.

1. Discover the repo root, branch/revision, working-tree changes, existing instructions, package/workspace files, CI and docs. Inventory paths before reading contents. Exclude secrets, generated outputs, dependency trees and large binary assets. Never print .env values, signing material or customer data.
2. Establish the baseline from existing documented commands, without running arbitrary scripts blindly. Record passed, failed and unavailable checks independently. Missing tests are a gap, not a pass. Preserve all user changes; use a separate branch/worktree when available and suitable, never reset the tree.
3. Invoke guardian-icm-architect for System Map/restructure with the actual subject root and desired map shelf. Its human gates remain in force. If it is missing, report that and finish a useful read-only inventory; do not claim an ICM audit.
4. Distinguish live features, leftovers, unimplemented aspirations and uncertain claims. Cite source symbols/tests. Do not infer safety to delete from age or lack of local references.
5. Prepare an adoption report at an unused docs/work location (or use the existing project convention). Include current structure, proposed additions, preserved paths, factual conflicts, baseline evidence and a concrete migration table: source -> target -> reason -> incoming references -> verification -> rollback. Check case-insensitive destination collisions, symlinks and existing targets. Ask about external hardcoded consumers only for paths proposed to move.
6. Obtain approval for that concrete plan, as required by ICM; prior approval covering these exact changes suffices. No repeated approval for each routine file copy. If approval is pending, stop before migration while leaving the report ready to review.
7. Apply additively first. Copy ordinary documentation, verify byte hashes before editing, update links in the same change, then remove/archive originals only as approved. Never follow symlinks outside the project. Separate consolidation edits from byte-preserving moves so verification remains meaningful. Keep a migration log of before/after hashes and paths. Preserve original content in version history or a local backup if not tracked; do not commit unrelated files.
8. Integrate Claude routing and Matt-compatible config per integration.md. Use root GLOSSARY.md for terms, docs/map for ICM operations. Preserve meaningful project instructions. Do not enforce an earlier chat's example folder layout on an established repo.
9. Validate every planned source/target and referrer. Re-run baseline checks when their inputs changed. Compare source-code/config hashes or diffs to prove documentation-only adoption left runtime inputs unchanged, excluding newly added documentation and skill files. If a broken test predated adoption, retain that evidence; do not label the whole project green.
10. Cold-walk from CLAUDE.md: locate an actual feature, its approved behavior, owning code, first-order consumers and tests using entry/map/card. Record missing knowledge as missing. Report added/moved/archived files, untouched runtime scope, baseline delta, rollback route and remaining risks.

Do not automatically migrate production data, rename source modules, rewrite imports or flatten monorepos. If required later, make a separate behavior-preserving change with characterization tests and authorization.
